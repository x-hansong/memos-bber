# Manual Sync Button And Schedule Diagnosis

## Problem Frame
当前 MinIO 配置同步已经有“保存设置后立即同步”和“按周期自动同步”的设计，但设置页缺少一个可显式触发的“立即同步配置”入口。与此同时，用户感知到“定时同步没有生效”，需要先把期望行为定义清楚，并在实现前明确最可能的失效点。

从现有代码看，这项工作是对既有同步能力的扩展而不是重做：后台已经有 `runSyncCycle()`、`chrome.alarms` 调度和同步状态存储，设置页也已经展示同步状态。最小且最清晰的方向，是在现有设置页增加一个手动触发入口，直接复用后台同一条同步链路。同时，同步范围不应继续依赖手工维护白名单，而应覆盖“设置页里的持久化配置”这一完整集合，避免以后新增配置项时漏同步。

## Requirements
- R1. 在设置页 MinIO 配置同步区域新增“立即同步配置”按钮。
- R2. 点击该按钮时，只同步已经保存到扩展存储中的配置，不读取也不提交当前表单里尚未保存的改动。
- R3. 该按钮触发的同步行为复用现有完整同步逻辑：可能推送本地到远端，也可能在双向同步开启时拉取远端覆盖本地。
- R4. 手动触发后，设置页需要能看到本次同步的最新状态，而不是继续停留在旧状态。
- R5. 定时同步的状态展示需要在后台状态变化后可见，避免“后台已执行但设置页看起来没生效”的误判。
- R6. 当同步配置不完整或请求失败时，手动触发和定时触发都应保留明确的失败状态与原因。
- R7. 同步范围应覆盖设置页里的全部持久化配置，不再依赖手工维护的同步白名单。
- R8. 运行时临时状态仍然不进入同步范围，例如只为当前交互存在的临时键不能被写入远端。

## Success Criteria
- 用户无需修改配置，也能在设置页主动发起一次完整同步。
- 用户能区分“未保存表单”和“已保存配置”的边界，不会因为按钮误触发隐式保存。
- 当后台定时同步执行后，设置页能反映最新状态，减少“定时同步失效”的错觉。
- 定时同步真实失败时，页面能显示可定位的问题线索，而不是只表现为“没有反应”。
- 后续新增设置页配置项时，无需再单独修改同步白名单也能被自动纳入同步。

## Scope Boundaries
- 不修改同步冲突策略，继续沿用现有“较新配置覆盖较旧配置”的规则。
- 不新增版本历史、回滚、差异预览或人工冲突处理界面。
- 不把“立即同步配置”做成“保存并同步”的复合按钮。
- 不在这次需求里重做整套 S3/MinIO 配置模型。
- 不把 `chrome.storage.sync` 里的运行时临时键一并同步到远端。

## Key Decisions
- 按钮只同步已保存配置：避免一个按钮同时承担“保存”和“同步”两种语义。
- 手动按钮复用完整同步链路：保证手动触发与自动触发行为一致，减少两套逻辑漂移。
- 先优先修复状态可见性问题：从静态代码看，定时同步“看起来没生效”的最可能主因是设置页没有订阅后台状态变化。
- 去掉手工同步白名单限制，但保留“仅同步设置页持久化配置”的边界：以后新增配置项默认进入同步范围，运行时临时状态仍排除在外。

## Dependencies / Assumptions
- 假设 `chrome.alarms` 在当前扩展权限与 Manifest V3 service worker 配置下可正常唤醒后台。
- 假设用户所说“没有生效”主要指设置页上看不到定时同步结果，而不是已经抓到明确的后台报错日志。

## Outstanding Questions

### Deferred to Planning
- [Affects R4][Technical] 手动同步完成后，设置页是通过消息回调主动刷新状态，还是通过监听存储变化自动更新状态。
- [Affects R5][Needs research] 是否需要额外补一个 `chrome.alarms.get()` 或调试日志入口，帮助判断闹钟是否真的创建成功。
- [Affects R6][Technical] 是否要把后台内部 `reason` 映射成更易懂的用户提示文案，而不是直接展示内部状态码。
- [Affects R7][Technical] 如何定义“设置页持久化配置”的唯一来源，避免导出、导入、保存和同步各维护一套键列表。
